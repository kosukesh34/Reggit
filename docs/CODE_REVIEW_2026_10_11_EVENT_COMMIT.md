# 決済イベント配送のコミット境界

## 指摘

PostCommitDomainEventDispatcher は内側のトランザクションが戻った直後に通知とポイント同期を実行していた。呼出し側が外側のトランザクションを持つ場合、ロールバックで注文・送信要求が消えても外部配送は取り消せない。Webhook のフォールバックジョブ投入にも同じ境界が必要だった。

調べた通常の決済 Controller と管理注文の本番経路では、追加の外側トランザクションは見つかっていない。公開された入れ子トランザクションの契約違反として修正し、通常経路での発生を確認したとは扱わない。

## 修正

送信要求の record はトランザクション内で保存し、実配送と listener 実行は DB::afterCommit へ移す。トランザクションがない場合は即時実行する。Webhook の直接ジョブ投入も最終コミット後へ遅延する。

遅延 callback は呼出し時の project と StoreContext の選択状態を保存し、その状態で実行して finally で復元する。HQ・未選択の状態も保持する。同期キューでジョブが即時実行されても別店舗を参照しない。既存の listener 例外をログへ残し、確定した操作結果へ伝播させない挙動は維持する。

## 検証

- 修正前に新しい6ケースを実行し、対象の早期配送・ジョブ投入を5ケースで検出。1ケースは既存のコンテキスト復元が成功。
- 修正後は決済確定・Webhook・注文フロー・dispatcher の関連27テスト、148アサーション成功。
- 実DBで最終コミット前の配送ゼロ、外側ロールバックで配送ゼロ、最終コミット後の配送1回を確認。
- Webhook の実Jobを sync キューで動かし、注文店舗Aで配送した後、呼出し元の別 project / 店舗Bへ戻ることを確認。
- listener が例外を投げてもHQ選択と後続呼出し元の選択を保持。観測値のassertionは例外吸収の外側に置く。
- Pint 6ファイルと既存ルールの全PHPStan（1 worker）成功。実行は隔離Docker / MySQL、外部APIはモック。

マージ前は最新mainを含む最新PR HEADへ全ローカルCIを実施する。外部サービスへの実接続や、プロセス停止時の外部配送のexactly-once保証は検証・実現していない。
