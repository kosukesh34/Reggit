# Kitchen／Waiting 店舗端末仕様

最終更新: 2026-09-27

## 1. 対象と基本方針

本仕様は、店舗で利用する次のiPadアプリを対象とする。

- Reggit Kitchen: 注文確認と調理ステータス更新
- Reggit Waiting: 順番待ち受付、呼出、再呼出、入店処理

アプリのバイナリは全プロジェクト共通とする。ビルド時にプロジェクトを固定せず、初回の端末登録によって接続先プロジェクトを確定する。登録後、APIトークンを別プロジェクトや別アプリ種別へ流用することはできない。

## 2. 端末登録

### 2.1 制約

| 項目 | 仕様 |
| --- | --- |
| 登録可能台数 | 1プロジェクトにつき、Kitchen 1台、Waiting 1台 |
| 発行者 | システム管理者、プロジェクト管理者、店舗管理者 |
| スタッフ | 発行不可。管理画面にも発行UIを表示しない |
| 登録コード | Kitchen／Waitingごとに個別発行。一度使用すると再利用不可 |
| コード保存 | 平文は発行直後の画面で一度だけ表示。DBにはSHA-256ハッシュのみ保存 |
| 端末認証期限 | 期限なし。再発行、ログアウト、管理上の失効まで有効 |

### 2.2 登録手順

1. 店舗オーナーが管理画面の「設定 → 基本設定 → 店舗端末の登録」を開く。
2. KitchenまたはWaitingの「登録コードを発行」を押す。
3. 画面に一度だけ表示されたコードを、対象iPadの初回起動画面へ入力する。
4. アプリが端末固有鍵を生成し、登録コード、アプリ種別、端末名とともに登録APIへ送信する。
5. サーバーがコードを消費し、プロジェクト・アプリ種別に限定したBearerトークンを発行する。
6. アプリはBearerトークンと端末固有鍵をiOS Keychainへ保存する。

### 2.3 再発行

登録コードを再発行した時点で、同じプロジェクト・アプリ種別の既存Bearerトークンを削除する。旧端末は次回APIアクセスから401となり、新しいコードで登録した端末だけが利用できる。

端末交換、紛失、盗難、Keychain消去時は再発行を行う。登録コードの平文を紛失した場合も、既存コードを表示し直さず再発行する。

## 3. API認証

### 3.1 登録API

`POST /api/store-app/login`

リクエスト:

```json
{
  "enrollment_token": "XXXXXXXX-XXXXXXXX-XXXXXXXX",
  "app": "kitchen",
  "device_name": "店舗iPad",
  "device_key": "端末で生成した十分に長いランダム値"
}
```

`app` は `kitchen` または `waiting`。成功時はBearerトークンとプロジェクト情報を返す。登録コードが不正、使用済み、またはアプリ種別が異なる場合は422を返す。

### 3.2 登録後のリクエスト

すべての店舗端末APIで次の両方を必須とする。

```http
Authorization: Bearer <token>
X-Device-Key: <device-key>
```

サーバーは以下を毎回検証する。

- Bearerトークンが有効である
- トークンのアプリ能力が要求先と一致する
- トークンのプロジェクト能力がURLのプロジェクトと一致する
- 管理者が現在も対象プロジェクトへアクセス可能である
- `X-Device-Key` のSHA-256ハッシュが登録時の端末鍵と一致する
- 対象プロジェクトが有効である

Bearerトークンだけ、または端末鍵だけでは認証できない。トークンと端末鍵はログへ出力しない。

### 3.3 主なAPI

| アプリ | API |
| --- | --- |
| Kitchen | `/api/kitchen/{project_key}/orders...` |
| Waiting | `/api/store-app/waiting/{project_key}/queue...` |
| Waiting・指定呼出 | `POST .../queue/{id}/call` |
| Waiting・次を呼出 | `POST .../queue/call-next` |
| Waiting・再呼出 | `POST .../queue/{id}/recall` |
| Waiting・入店 | `POST .../queue/{id}/enter` |

## 4. 画面操作

### 4.1 Kitchen

- 注文カードのボタンで次のステータスへ進められる。
- 注文カードを左へ90pt以上スワイプしても同じ操作を実行できる。
- 縦スクロールを誤認しないよう、横方向の移動量が縦方向より大きい場合だけスワイプとして扱う。
- スワイプ後もサーバー更新が成功するまではAPIの結果を正とする。

### 4.2 Waiting

順番待ち一覧の行を左へスワイプすると状態に応じた操作を表示する。

| 現在の状態 | スワイプ操作 |
| --- | --- |
| 待機中 | 呼び出し |
| 呼出済み | 入店（フルスワイプ）、再呼出 |

従来の画面内ボタンと「次を呼び出し」も残す。指定呼出は選択した受付だけを呼び出し、先頭の別受付には影響しない。不正な状態遷移は422として扱う。

## 5. データ

`store_app_credentials` はプロジェクトとアプリ種別の組み合わせを一意とする。

| カラム | 用途 |
| --- | --- |
| `project_id`, `app` | 店舗・アプリの一意な登録枠 |
| `admin_user_id` | 登録コード発行者 |
| `personal_access_token_id` | 現在有効なSanctumトークン |
| `enrollment_token_hash` | 未使用登録コードのハッシュ。使用後はNULL |
| `device_key_hash` | 登録端末鍵のハッシュ |
| `device_name` | 管理画面に表示する端末名 |
| `enrollment_created_at` | 登録コード発行日時 |
| `claimed_at` | 端末登録完了日時 |

## 6. 導入と検証

デプロイ時に次を実行する。

```bash
php artisan migrate --force
```

認証境界の回帰テストは `StoreAppAuthenticationTest`、管理画面の発行・失効は `AdminSettingsTest`、Waiting操作は `QueueApiTest` で確認する。外部スマレジ実接続を除く全テスト、Pint、TypeScript型チェック、Kitchen／Waitingのシミュレータビルドをリリース前に実行する。
