# Reggit — 作る理由

## この文書について

この文書は、Reggit に関わる次の人のための共通説明書である。

- 導入を検討している店舗、実際に利用する店舗スタッフ
- Reggit の Git リポジトリで開発、レビュー、保守を行う人

前半では「Reggit が何を解決するか」を利用者にも分かる言葉で説明する。後半では、プロダクトの目的を実装へ反映するために、開発時の判断基準をまとめる。

画面・機能の詳細は [FEATURES_SPEC.md](FEATURES_SPEC.md)、システム構成は [ARCHITECTURE.md](ARCHITECTURE.md)、スマレジ連携の設定は [SMAREGI_SETUP.md](SMAREGI_SETUP.md) を参照する。

## Reggit とは

**Reggit は、会員証、ポイント、クーポン、注文、予約、順番待ちを、スマレジの会員・購買情報とつなぐ店舗向けサービスである。**

顧客は LINE ミニアプリまたは iOS / Android アプリを利用する。店舗では Web 管理画面に加え、順番待ち受付とキッチンモニターの iPad アプリを利用できる。

Reggit の目的は、会員証をデジタル化することだけではない。来店時の便利な体験を入口に、会員情報と購買情報を蓄積し、店舗が無理なく再来店につなげられる状態を作ることである。

> 便利な来店体験 → 会員化 → 購買情報の蓄積 → 特典・案内 → 再来店

## なぜ Reggit が必要か

### 店舗の課題

店舗では、POS、会員証、LINE、注文、予約、順番待ちが別々に運用されることがある。情報が分かれていると、顧客がいつ来店し、何を購入し、どの特典を利用したかを一貫して把握しにくい。

また、小規模な店舗では、専任担当者が顧客分析やキャンペーン設定を続けることが難しい。高機能でも、毎日の操作や設定が複雑なシステムは定着しない。

Reggit は、次の状態を解消するために作る。

- 会員情報と購買・来店情報が分かれている
- 会員を集めても、再来店につながる施策を継続できない
- 注文、予約、順番待ちが別サービスに分散している
- 設定や分析に使える時間と専門知識が限られている

### 顧客の課題

顧客にとって、会員登録そのものは目的ではない。待ち時間が減る、注文が簡単になる、会員証をすぐ提示できる、使える特典が分かる、といったその場の価値が必要である。

Reggit は、顧客に次の操作を強いない。

- 会員証を表示するための長い画面遷移
- 利用のたびに必要となる複雑なログイン
- 内容や理由が分からない大量の通知
- 店舗ごとに異なる操作を覚えること

## Reggit が提供する価値

| 利用者 | 実現したいこと | Reggit が提供するもの |
|---|---|---|
| 店舗オーナー・店長 | 少ない手間で再来店を増やしたい | 会員・購買情報、クーポン、低頻度の自動配信をまとめて管理する仕組み |
| 店舗スタッフ | 接客、受付、調理、会計を滞らせたくない | 会員証、注文、予約、順番待ちを一つの店舗情報にまとめた運用 |
| 顧客 | 待つ、注文する、特典を使う手間を減らしたい | LINE またはアプリから利用できる短い導線 |
| 多店舗運営者 | 店舗ごとの運用を守りながら管理したい | 店舗単位のデータ分離と、将来の本部・ブランド管理を見据えた構成 |

主な対象は飲食店と物販店である。会員証、ポイント、スタンプ、クーポンは業種を問わず利用できる。注文、予約、順番待ちは、必要な店舗だけが有効にする。

### 顧客向けの入口

| チャネル | 用途 |
|---|---|
| LINE ミニアプリ（LIFF） | アプリを追加インストールせず、会員証、注文、予約、順番待ちなどを利用する |
| iOS / Android アプリ | LINE と共通の機能を店舗・ブランドのアプリとして利用し、プッシュ通知を受け取る |

### 店舗向けの入口

| チャネル | 用途 |
|---|---|
| Web 管理画面 | 商品、注文、会員、予約、順番待ち、スタンプ、クーポン、お知らせ、画面デザインを管理する |
| Reggit Wait（iPad） | 店頭で順番待ちを受け付け、受付番号と QR コードを発行する |
| Reggit Kitchen（iPad） | モバイル注文を確認し、調理中、受取可、完了の状態を管理する |

ネイティブアプリの構成とビルド方法は、[顧客向け iOS / Android アプリ](../mobile/reggit-skip/README.md) と [店舗向け iPad アプリ](../ios/README.md) を参照する。

## 利用者に約束すること

### すぐに使える

- 会員証は起動後すぐに提示できる
- 顧客は LINE とネイティブアプリから、店舗に合う入口を選べる
- ネイティブアプリのインストールを、すべての顧客の利用条件にはしない

### 店舗で運用し続けられる

- よく使う設定には分かりやすい初期値を用意する
- 通常運用に複雑な分析や細かなセグメント設定を要求しない
- 必要のない機能は無効にできる

### 通知を送りすぎない

- 自動配信は、休眠、誕生日、会員ランクなど、受信理由が分かるものを基本とする
- 送信通数ではなく、特典の利用と再来店を重視する
- 通知を使わなくても、会員証、注文、予約、順番待ちに価値がある状態を作る

### 情報を安全に扱う

- 顧客情報を、利用している店舗の範囲を越えて混在させない
- 再来店体験の改善に必要な情報だけを扱う
- 顧客に説明できない判定や、不透明な自動配信を行わない

## 開発者が守る基準

### 中心となる機能

- デジタル会員証
- ポイント、スタンプ、クーポン
- モバイルオーダー、予約、順番待ち
- スマレジの会員・購買情報との連携
- LINE / LIFF と iOS / Android アプリ
- 店舗が短時間で完了できる初期設定
- 店舗単位のデータ分離

これらは独立した機能として増やすのではなく、同じ会員と店舗の情報でつなぐ。入口機能だけでは便利なツールで終わり、配信機能だけでは必要な顧客接点と情報を得られない。入口から再来店までをつなぐ改善を優先する。

### データ境界

現行実装では、`projects` の1件が1店舗であり、`project_id` がテナント境界である。モデル、クエリ、キャッシュ、ジョブ、ログ、外部連携のすべてで、この境界を守る。

将来は、1社・1ブランドが最大 300 店舗を管理できる構成を目標とする。ただし、現在の `project_id` をブランド単位として扱ってはならない。本部機能を追加するときは、店舗の上位に組織階層を設け、権限、設定継承、集計範囲を明示する。

### 安定性

- 二重決済、ポイントの二重付与、クーポンの二重発行、通知の二重送信を防ぐ
- Webhook とバッチは、同じ処理を再実行しても結果が重複しないようにする
- LINE、スマレジ、Stripe など一つの外部サービスの障害で、無関係な機能まで停止させない
- 300店舗を超えるサービス全体の処理を想定し、全件一括ではなくページング、キュー、店舗単位の分割を使う

### 変更時のチェックリスト

Issue、設計、実装、コードレビューでは、次を確認する。

1. 顧客の来店体験を簡単にするか、店舗の再来店づくりを助けるか
2. 会員、来店、購買、再来店のつながりを強くするか
3. 専任担当者がいなくても導入・運用できるか
4. 顧客に、取得する情報と提供する価値を説明できるか
5. 通知、設定、画面、外部依存を必要以上に増やさないか
6. 店舗間のデータ分離と、障害・再実行時の安全性を保てるか
7. 効果を測り、継続または廃止を判断できるか

明確に答えられない変更は、範囲を小さくして検証するか、実装しない。
