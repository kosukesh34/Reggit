# 管理画面の会員編集における保存の原子性

## 指摘

管理編集では、氏名・メールなどの User 更新が Member とランク履歴のトランザクションより先に確定していた。会員保存が失敗しても User だけが変更され、フォーム全体が失敗したという結果と保存状態が一致しない。

## 修正

User → Member の順で行ロックを取得し、両者の更新と既存のランク履歴・ランク送信要求を同じトランザクションに含める。読み込み時の user_id とロック後の user_id が一致しない場合は、旧ユーザーが削除済みでも更新を拒否する。

## 確認

- 会員保存例外で氏名・メール・状態がすべて元に戻る。
- 成功時は氏名・メール・状態が保存される。
- 所有ユーザー変更後の古い Member インスタンスは、旧ユーザー・新ユーザー・会員状態を変更しない。
- 旧ユーザーが soft delete 済みでも古いインスタンスの更新を拒否する。

上記4テスト、14アサーションが隔離 Docker / MySQL で成功。既存のランク履歴・ランク再送を含めた関連17テスト、104アサーションも成功。Pint（2ファイル）と既存ルールの全PHPStan（検証環境のメモリ制限のため1 worker）も成功。マージ対象コミットの全ローカル CI は別途実施する。

## 残る範囲

外部プロフィール送信の永続化、nullable 項目の明示的なクリア、profile_extra の部分更新は別の指摘として継続して修正する。本変更だけで管理編集の外部同期が解決したとは扱わない。
