# 会員取得時の現在所有者確認

## P1: 移管後のプロフィールを元のユーザーへ返す

MemberService::getMemberDataはcached User.memberをrefreshし、現在のmember.userからプロフィールを生成していました。会員取得後に移管がcommitすると、移管先のname/email/phone等を元ユーザーへ返せます。削除後は台帳補正のdefault scope付き取得が例外になります。外部取得中に移管・削除されるケースも同じ問題を持ちます。

最初はキャッシュを使わず、user relationと明示projectで現在の会員を取得します。登録復旧後も同じ会員・project・所有者を確認します。外部ポイント取得後はtransaction内でその会員をロックし、台帳補正・プロフィール投影をそのロック内で完了します。同期・登録復旧の外部I/Oはロック外に維持します。確認できない場合は既存ゲスト応答へ戻ります（profile=[]含む既存形を維持）。

## 根拠と検証

- cached移管・削除、同期callback中の移管・削除の4ケースを追加。修正前4失敗・6成功（29 assertions、6.40秒）、修正後10成功（38 assertions、5.65秒）。
- ポイント鮮度・ランク履歴・複数店舗を含む61テスト226 assertions成功（7.69秒）。取得時に外部ポイント120を取り込む既存契約も維持。
- 最終所有者照合を隔離コピーで外すmutationは同期中移管の1ケースが失敗（60成功、224 assertions、7.23秒）。
- 独立5軸レビューでブロッカーなし。外部HTTPはmockで、実API・本番は未確認。

最新HEADへ指定merge-pr.shで全ローカルチェックを新規実行し、成功時のみマージします。GitHub Actions結果は使用しません。

## 設計判断

会員データmoduleのinterfaceで現在の所有者を確認し、確認と投影のseamにロックを置きます。正しさのlocalityを共通module内に保持し、既存controller・Wallet経路に修正のleverageが届きます。読み取りと同期の全面分離は既存鮮度契約を変えるため、この修正では行いません。guest投影を一度定義し、所有者が消失した前後の経路で同じ応答を使います。
