# セキュリティ・コード・UIレビューと修正（2026-09-23）

認証、店舗分離、会員・端末、順番待ち、注文・在庫・決済、HTML出力、依存関係、UIとCIを確認した。既存の機能変更はPR #238に分離し、レビューによる修正と回帰テストを別PRにまとめた。

## 導入時の手順と互換性

1. PHP 8.4、Node ^20.19.0 または >=22.12.0を使用し、依存関係をインストール・アセットをビルドする。
2. `php artisan migrate --force` でorders.payment_sessionとuser_devices.auth_tokenを追加する。暗号化には既存APP_KEYを使用するためキーを変更しない。
3. 管理画面の基本設定で店舗端末トークンを発行し、更新した受付・キッチンアプリの設定へ入力する。古いアプリや未設定端末は管理操作を拒否される。再発行後は全端末を再設定する。
4. 顧客用ネイティブアプリもサーバーと同時に更新する。旧レコードは秘密トークンを持たないため、識別子だけの自動引継ぎは行わない。既存の認証済みセッションまたはLINE本人確認で同じ所有者を確定できる場合に発行できる。既存のゲスト会員は、管理者が本人確認・復旧手続きを行う必要がある。識別子だけで所有者を付け替えない。
5. トークンはアプリ専用ストレージ（WebViewは同一オリジンlocalStorage、SwiftはアプリのUserDefaults）に保存する。配信はHTTPSを使用する。今回、OSキーチェーンへの移行は含めていない。
6. 決済セッション保存前に発行された未完了Intent/Checkoutは移行対象外。リリース前にStripe側の未完了決済を照合・解消する。保存したCheckout URLには有効期限があるため、期限切れは注文の取消し・再作成で対応する。既存注文で別経路の決済を新設しない。

## 範囲の限界

本番へのデプロイ、実Stripe課金、外部スマレジ・LINE・Push連携、iPad実機の印刷・通知、Android実機E2Eは未実施。並行注文の行ロックを実装したが、複数プロセスを使う負荷試験は未実施。SkipのSwiftテストには既存のObjective-Cクラス重複警告がある。これは主要境界のコード・ローカル実行レビューであり、全コードの無欠陥を保証するものではない。
