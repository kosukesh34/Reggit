# 新規会員登録の外部処理後の状態確認

## P2: 契約・登録要求・ユーザーが変わっても登録が確定する

MemberService::registerMemberは登録要求を永続化してから外部顧客を作成または回復し、ローカルで会員・プロフィール・初回特典を保存する。外部処理後の確定では契約と登録要求を再確認せず、Userのロック取得結果も無視していた。契約変更時に旧契約の顧客IDが保存され、登録要求の世代が変わった場合には古い応答が新世代の要求を削除する。ユーザー削除時にも確定が進む。

## 修正

開始時のプロジェクトを確定トランザクションへ引き継ぎ、現在のUserをID・プロジェクトでロックする。登録要求がある場合は、要求ID・所有者・プロジェクト・世代・会員番号・契約と現在の契約をロック下で照合する。不一致は会員作成・プロフィール更新・初回特典発行の前に中断する。成功時だけ再取得した登録要求を削除する。

User→Projectの既存ロック順は維持する。Projectロックは無予約の会員番号採番時だけ取得する。外部HTTPは確定トランザクション外のまま。外部応答nullでもidentityが一致する任意登録のローカル確定は維持する。

既存の登録moduleへ最終的な保存条件を閉じ込め、HTTP adapterとローカル保存のseamでlocalityを強める。新たなinterfaceやラッパーは追加しない。登録復旧はPR354で別途修正済み。

## ローカル検証

- 修正前: 4回帰ケースが失敗（16 assertions、24.58秒）。契約変更の必須/任意登録、要求世代更新、User削除でも登録が拒否されないことを確認。
- 修正後: 会員API・外部ポイント取り込み・登録復旧を含む45テスト成功（189 assertions、79.73秒）。
- 確定前の状態確認を除去したmutationで4回帰が失敗（16 assertions、23.18秒）。
- 独立静的レビューでblockerなし。呼び出し元は登録結果の現在情報を再取得するため、ロック済みUserモデルでの保存にも互換性問題を確認しなかった。

外部POSTモック内で状態変更を行い、HTTP時点のトランザクションなしも確認する。別プロセスでの同時変更・本番スマレジ接続・ブラウザE2Eは未検証。既に外部作成された顧客の削除は行わず、登録要求を保持して既存の登録marker照合ルールに従う。契約変更時は既存の管理者確認エラーで中断する。
