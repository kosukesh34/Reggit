# 注文ポイントの所有者確認とロック

## P2: 検索後の会員移管で旧ユーザーのポイント操作が新所有者へ届く

注文ポイント更新と未決済取消は、ユーザーIDから会員を検索した後、会員IDだけでロックしていた。間に会員の所有者が変わると、移管後の会員へ消費・獲得・返却・取消が保存され得る。台帳同期も所有者ロックより前だった。

## 修正

MemberRepositoryにfindByUserIdForUpdateを追加し、所有者・プロジェクト・削除状態を含む現在読み取りで会員をロックする。ポイント更新はこのロック取得後に台帳同期し、残高を再取得する。取消も直接この操作を利用する。本番の注文作成・決済確定・取消は外側トランザクション内で呼び出すため、ロックはポイント保存まで維持される。

検索とロックの契約をリポジトリのinterfaceへ集約し、Eloquent adapterに実装を閉じ込める。moduleのseamに所有者確認を含めることでlocalityが改善し、呼び出し元がIDだけのロックへ退行することを防ぐ。既存のID検索契約と残高計算は維持する。

## ローカル検証

- 修正前: 2失敗・23成功、103 assertions、7.07秒。移管後消費が拒否されず、取消で新所有者に30ポイントを返却。
- 修正後: 41成功、161 assertions、27.06秒。既存の取消冪等性・残高並行処理・会員リポジトリ・注文APIを含む。
- 所有者条件だけを除いたmutation: 2失敗・39成功、158 assertions、27.83秒。両回帰テストが誤消費・誤返却を検出。
- 独立の静的レビュー: blockerなし。

新しい移管回帰テストはSQL実行直前のcallbackで順序を再現する。別プロセスの所有者移管や本番外部API接続は検証していない。ランク再計算のキャッシュ選択など、具体的な誤付与を未確認の候補は今回変更しない。
