# 登録復旧の所有者・契約の再確認

## P2: 外部顧客検索中の変更で別所有者・別契約へ誤連携する

MemberServiceの会員データ取得はMemberRegistrationRecoveryを呼び、曖昧な外部登録応答から既存顧客IDを回復する。復旧はHTTP前に登録要求を照合するが、HTTP後は会員IDのみでロックしていた。検索中に所有者が移管されると、旧所有者の顧客IDが移管先会員へ保存され、登録要求も削除される。契約変更時も旧契約の顧客IDが保存される。

会員データ取得側の後続の所有者確認は返却を防ぐだけで、復旧による誤保存を防げない。

## 修正と設計

HTTP前の所有者・プロジェクトを固定し、User→Member→登録要求の順を維持して現在状態をロックする。MemberはID・プロジェクト・所有者が一致するときだけ取得する。登録要求の世代・所有者・プロジェクト・会員番号・契約と現在契約を再照合してから顧客IDを保存し、確認した登録要求だけ削除する。不一致は復旧を中止し、要求を保持する。外部検索はロック外のまま。

既存の登録復旧moduleへ整合性判断を閉じ込め、呼び出し元の表示projectionとのseamでのlocalityを保つ。新たなmoduleやinterfaceは追加せず、HTTP adapterから戻った結果を保存してよい条件を既存module内で強める。

## 検証

- 修正前: 所有者移管と契約変更の2テスト失敗、既存6テスト成功（42 assertions、48.45秒）。旧顧客IDの誤保存を確認。
- 修正後: 登録復旧8テスト成功（44 assertions、48.49秒）。通常の応答不明からの復旧、ロールバック後の再利用、別顧客の拒否、外部検索失敗時の二重作成防止を維持。
- 関連の会員API・外部ポイント取り込みを含む41テスト成功（162 assertions、55.18秒）。
- 保存直前の所有者・契約確認を除去したmutationで2回帰が失敗（6 assertions、11.93秒）。
- 独立の静的5軸レビューでblockerなし。

回帰はAPIモックのGET callbackで移管・契約変更を行う。外部GETの時点ではDBトランザクションがないことも確認する。別プロセスの移管と本番スマレジ接続は未検証。会員データ取得の責務分割やWalletでの重複取得はoptionalな設計候補で、この修正には含めない。
