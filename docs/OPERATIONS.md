# 管理・店舗運用

## 入口と役割

| 対象 | 入口 | 主な操作 |
|---|---|---|
| 顧客 | `/liff/{project_key}`、ネイティブアプリ | 会員証・注文・予約・受付・特典 |
| 店舗・本部 | `/admin/{project_key}/login` | 日次運用・店舗設定・配信・分析 |
| システム管理者 | `/system-admin/login` | プロジェクト・アカウント・API トークン・全体監査 |
| 新規導入 | `/onboarding` | プロジェクト・管理者・連携情報の登録 |

| ロール | 範囲 |
|---|---|
| `system_admin` | システム管理とアクセス可能プロジェクトの管理 |
| `project_admin` | 担当プロジェクトの全店舗、店舗追加・担当者割当 |
| `admin` | 担当店舗の日次運用 |
| `staff` | 担当店舗かつ付与された機能別権限 |

スタッフ以外は機能別権限チェックを省略しますが、プロジェクト・担当店舗・プランなどの制約は残ります。スタッフの権限はシステム管理のアカウント編集で設定し、キーの正確な一覧は `AdminUserPermission::ALL_PERMISSIONS` / `PERMISSION_GROUPS` を参照します。

## 複数店舗

本部が管理画面の「店舗管理」で店舗と担当者を登録します。本部は「全店舗」を選択できますが、注文・予約・受付の作成には具体的な店舗を選びます。支店は担当店舗だけを選択でき、担当がなければ会員・取引を表示しません。

| 情報 | 範囲 |
|---|---|
| 会員証・会員番号・ポイント残高・ランク | プロジェクト共通 |
| 会員閲覧 | 本部は全会員、支店は利用関係のある会員 |
| 注文・予約・受付・来店・取引履歴 | 実際に利用した店舗 |
| 会員メモ | 複数店舗では店舗ごと |
| 営業時間・休業日・注文モード・予約枠・定員・受付設定 | 店舗で上書き。未設定はプロジェクト値 |
| 商品・価格・在庫・特典定義・タグ・ブランド・LINE | プロジェクト共通。本部が編集 |
| 店舗端末認証 | 発行店舗に固定 |

共通プロフィールの変更・退会、共通商品・配信ルールの編集は複数店舗では本部に限定します。1店舗の間は従来の管理権限を維持します。

LIFF の選択店舗は `?store_id={id}`、API は `store_id` / `X-Store-Id` を使います。店舗の表示だけでは会員との利用関係を追加しません。

プロフィールの「対象店舗」は `members.customer_store_id` に保存し、スマレジ送信時に対応する `smaregi_store_id` へ変換します。対応不明なら外部IDを送信せず、受信でも既存値を上書きしません。対象変更で過去の利用関係・取引店舗・共通残高を消しません。

既存プロジェクトの初期店舗は `main` です。異なるプロジェクトの統合は LINE 契約・会員識別・スマレジ契約・ポイント対応を確認する別の移行として扱います。

## 配信

支店の「全員」は選択店舗の利用会員、本部の「全店舗」はプロジェクト全体です。個人指定・条件指定・LINE / Push 送信にも同じ店舗制限を適用し、重複送信を避けます。

対象限定お知らせとその画像は対象会員だけが閲覧できます。予約配信は実行時も作成者の権限・担当店舗・店舗の有効状態を確認し、失効していれば `held` にします。本部は対象を確認して新しい配信を作り、保留分を削除します。自動で対象を広げません。

任意の複数店舗をまとめて選ぶ配信、店舗別商品価格・在庫・タグ・通知拒否、本部の再承認ボタンは現在の標準機能として扱いません。

## Kitchen / Waiting の端末登録

店舗端末アプリは全店舗共通のビルドを使い、初回登録で店舗を確定します。各店舗・各アプリにつき1台です。

1. システム管理者・プロジェクト管理者・店舗管理者が「設定 → 基本設定 → 店舗端末の登録」で Kitchen または Waiting のコードを発行する。スタッフは発行できない。
2. 一度だけ表示されるコードを対象 iPad に入力する。
3. アプリは端末固有鍵を生成し、登録 API に送信する。
4. 発行された Bearer トークンと端末鍵を Keychain に保存する。

```http
POST /api/store-app/login
Content-Type: application/json
```

```json
{
  "enrollment_token": "発行された登録コード",
  "app": "kitchen",
  "device_name": "店舗iPad",
  "device_key": "端末で生成したランダム値"
}
```

`app` は `kitchen` / `waiting`。不正・使用済み・種別不一致の登録コードは拒否します。DB は登録コードと端末鍵のハッシュだけを保存します。

登録後の API は `Authorization: Bearer <token>` と `X-Device-Key` の両方を送り、店舗・アプリ能力・発行管理者の現在の権限を照合します。トークンは期限なしで、再発行・ログアウト・管理上の失効まで有効です。コードの再発行で旧端末は即時失効します。平文コードは再表示せず、紛失・交換時は再発行します。

| アプリ | API | 操作 |
|---|---|---|
| Kitchen | `/api/kitchen/{project_key}/orders...` | 注文確認・状態更新・Push 登録 |
| Waiting | `/api/store-app/waiting/{project_key}/queue...` | 受付・一覧・指定呼出・次番呼出・再呼出・入店 |

Kitchen の Push 登録は認証済み店舗に紐づき、その店舗の注文だけを通知します。既存端末の移行では、店舗が1件のプロジェクトだけ所属を自動設定します。複数店舗の所属不明端末には、認証済みの再登録まで通知しません。更新版アプリは起動・復帰・ログイン後に同じ Push トークンでも再登録します。旧版を使い続ける端末は「設定 → 保存」で再登録してください。

Kitchen のログアウトは進行中の Push 登録を待ち、通知登録の解除を試みた後、通信失敗時もローカルの資格情報を消します。登録・解除の通信タイムアウトはそれぞれ5秒です。解除に失敗するとサーバーの通知登録が残ることがあるため、通信復旧後に同じ端末でログインし、再度ログアウトしてください。

Kitchen はボタンまたは横90pt以上の左スワイプで次状態へ進めます。Waiting は待機中なら呼出、呼出済みなら入店・再呼出を表示します。縦スクロールと区別し、サーバーの成功応答を正とします。不正な状態遷移は422です。ビルド方法は [iPad README](../ios/README.md) を参照してください。

## スタンプ・クーポン・取消

| カード設定 | 達成後 | 余り |
|---|---|---|
| 繰り返す（既定） | 次の周へ | 持ち越す |
| 1周で終了 | 終了。取消で未達成に戻り得る | 付与上限を超えた分は捨てる |
| 別カードへ切替 | 達成カードを履歴に残し次へ | 次カードへ持ち越す |

繰り返すカードの表示は現在の周の個数です。10個カードで累計14個なら4個、20個なら0個です。繰り返すカードの特典はマイルストーン設定を使い、`completed_at` を前提にした達成時トリガーは使いません。

| 会計キャンセル・返品の対象 | 処理 |
|---|---|
| その会計で付いたスタンプ | 実際の付与分を戻す |
| その会計で発行した未使用達成クーポン | 発行取消。同じ周を再達成すれば再発行 |
| 使用済み達成クーポン | 回収・未使用化しない。同じ周では再発行しない |
| 別の会計・別の周のクーポン | 変更しない |
| 会計由来の未使用ガチャ権利・未使用当選クーポン | 回収。使用済みは残す |
| スタンプ達成由来のガチャ | 会計取消では回収しない |
| ポイント | 付与分を戻す。スマレジ側残高連動は連携側の動きに従う |

同じ会計の再取消は重複処理しません。手動スタンプ減算・付与QRは会計との紐づきがないため、会計取消としてクーポンを回収しません。

例: 10個カードで9個から会計により5個を付けると、次周4個と達成クーポンになります。取消で9個へ戻り、クーポンが未使用なら取消・再会計で再発行、使用済みなら残り・同じ周の再発行はありません。1周終了カードなら実際の付与は不足分1個だけです。

調査先は `StampBalanceService`、`StampMilestoneRewardService`、`CouponIssueService::revokeUnusedForSource`、`SmaregiInboundAwardApplier`、`LotteryEntitlementService::revokePendingForSource`。発行元と `issue_grant_key` を確認し、`StampMilestoneRewardTest` で回帰を検証します。
