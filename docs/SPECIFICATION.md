# Mobile Order 仕様説明書（ドラフト）

本書は「このアプリがどのような思想で設計されているか」を軸に、現状コードと既存ドキュメントから読み取れる仕様を整理したものです。変更・補完のたたき台として使えるよう、意図とルールを明示しています。

---

**1. 目的と全体像**

- LINE（LIFF）/ブラウザで利用する「お客様向けモバイルオーダー」と、店舗運用のための「管理画面」を同一システムで提供する。
- BtoB を前提とした「複数店舗（プロジェクト）対応」を標準とし、URL とデータの双方でテナント分離を徹底する。
- 変更に強い構成を重視し、プレゼンテーション層・アプリケーション層・データ層の三層構造で責務を分離する。

**2. ユーザーと権限**

- お客様: LIFF/ブラウザで注文・予約・スタンプ・クーポン等を利用するエンドユーザー。1プロジェクトに紐づく。
- 店舗管理者: 担当プロジェクトのみを運用できる管理者。アカウント管理は不可。
- プロジェクト管理者: 担当プロジェクトのみを運用できる管理者。アカウント管理は不可。
- システム管理者: 全プロジェクト操作とアカウント管理が可能。

権限の表示名（管理画面で統一）
- system_admin
- project_admin
- admin

**3. 主要機能（お客様向け）**

- 商品一覧と注文作成
- 注文履歴の閲覧
- 会員証表示
- スタンプカードの閲覧
- クーポンの閲覧・利用
- 順番待ちの受付・状況確認
- 予約の受付・状況確認

**4. 主要機能（管理画面）**

- ダッシュボード（統計・直近注文）
- 注文管理（一覧・詳細・ステータス更新・完了）
- 商品管理（一覧・作成・編集・削除）
- 会員管理（一覧・詳細）
- 予約管理（一覧・詳細・ステータス更新・完了）
- 順番待ち管理（一覧・ステータス更新・待ち時間推定）
- スタンプ管理（一覧・作成・編集・削除）
- クーポン管理（一覧・作成・編集・削除）
- お知らせ管理（一覧・作成・編集・削除）
- 設定管理
- 基本設定（営業時間・予約枠・定休日・予約上限・順番待ち平均時間）
- 詳細設定（LINEテーマ色）
- メニュー設定（フロント表示タブ）
- システム管理者のみ: アカウント管理

**5. 主要URL**

お客様向け
- `/` または `/liff`: LIFF メイン画面

管理者向け
- `/store/login`: 店舗管理者ログイン
- `/admin/login`: 管理画面ログイン
- `/admin/{project_key}`: 管理画面トップ（ダッシュボード）

**6. アーキテクチャ思想（3層構造）**

- プレゼンテーション層（Controller / View）
- 入出力と画面表示のみに責務を限定し、業務ロジックは持たない。
- アプリケーション層（Service）
- ユースケースの実装とトランザクション制御を担う。HTTP や View に依存しない。
- データ層（Model / Migration）
- データ定義と永続化のみを担う。業務ロジックは原則持たない。

依存方向
- プレゼンテーション → アプリケーション → データ
- 逆方向依存は作らない。

**7. マルチテナント設計**

- 全テーブルに `project_id` を持たせ、データは project_id で完全に分離する。
- 管理画面のURLに `project_key` を含めることで、操作対象プロジェクトを明示する。
- `AdminContext` に現在プロジェクトを保持し、`ProjectScope` によってモデルのクエリに自動で `project_id` 条件を付与する。
- `bind.admin.project` ミドルウェアで URL の `project_key` を解決し、`AdminContext` に設定する。

**8. データ設計の思想**

- PII（氏名・メール・電話・住所・誕生日）は users / members のみに保持し、他テーブルには保存しない。
- ポイントの正（ソースオブトゥルース）は `point_transactions` のみ。`members.points` は表示用キャッシュ。
- キャンセル等の履歴が必要な取引は「削除ではなくステータスで表現」。
- テナント分離は `project_id` で徹底する。

**9. 設定設計（shop_settings）**

- `shop_settings` は key/value 型の設定ストアで、プロジェクトごとに設定値を保持する。
- 値の型は `type` で管理（string, integer, boolean, json など）。

主要な設定キー（現行実装）
- 営業時間: `business_hours_start`, `business_hours_end`
- 予約枠: `reservation_time_slots`
- 定休日: `closed_days`
- 休業日: `closed_dates`
- 事前予約日数: `advance_booking_days`
- 予約枠上限: `reservation_capacity_per_slot`
- 順番待ち平均対応時間: `queue_avg_serve_minutes`
- LINEテーマ色: `line_primary_color`, `line_primary_dark`, `line_success_color`, `line_danger_color`
- フロントメニュー: `frontend_menu_items`

**10. 予約の仕様（管理画面中心）**

- 予約一覧はステータスと日付で絞り込み可能。
- 指定日がある場合、日付別のステータス集計と時間帯別の埋まり状況を表示する。
- 時間帯ごとの満席判定は `予約数 >= 予約枠上限`。

**11. 順番待ちの仕様（管理画面中心）**

- 現在の待ち組数を表示する。
- 平均対応時間（分）をもとに、推定待ち時間を算出して表示する。

**12. 管理画面UIの基本構成**

- 左サイドバー＋右メインの2カラムレイアウト。
- 右メイン上部にページタイトルと操作バー（店舗切替・アカウント管理・ログアウト等）。
- 成功／エラー通知を上部に表示。
- 一覧系はテーブル＋ページネーションを基本とする。

**13. 実装規約（重要な思想）**

- Controller は FormRequest でバリデーションし、Service を呼ぶだけにする。
- Service は Request を受け取らず、プリミティブや DTO を受け取る。
- Model はデータの入出力に専念し、業務ルールは Service に置く。
- Enum と定数でマジックナンバーを排除する。
- 比較は `===` を原則とする。

**13.1 監査ログ**

- 管理画面の更新系操作（POST/PUT/PATCH/DELETE）は `admin_audit_logs` に記録する。
- 監査ログには admin_user_id / project_id / ルート名 / URL / IP / User-Agent / payload を保存する（パスワードは伏せる）。

**14. 外部連携（想定）**

- スマレジ POS 連携を想定した概念マッピングが存在する。
- 契約IDや外部IDは DB ではなく `.env` や `shop_settings` で管理する想定。

**14.1 API 方針（モバイルアプリ想定）**

- `/api/v1/*` をモバイルアプリ向けの安定APIとして提供する。
- 認証は **APIトークン方式**（`Authorization: Bearer` または `X-Api-Token`）を使用。
- トークンは **プロジェクト単位** で発行し、`api_tokens.token_hash` にハッシュを保存（平文は保持しない）。
- レスポンス形式は `{ success, message, data, meta }` を基本とする。
- system-admin で **APIトークンの発行/失効** が可能。

**14.2 API 移行方針（旧 /api から /api/v1 へ）**

- 既存の `/api/*` は **旧API** として維持するが、新規実装・改修は **/api/v1** のみに行う。
- 旧APIは **将来的に廃止予定**。移行期間中はフロント（LIFF）を順次 `/api/v1` へ切り替える。
- アプリ/外部連携は **/api/v1 のみ**を利用する。
- LIFF側は `api-base` を切り替えることで `/api` → `/api/v1` へ段階移行する。

**15. 代表的な業務フロー（例）**

商品作成（管理画面）
1. Controller が FormRequest で入力検証。
2. Service が `Product` を作成。
3. 成功時に一覧へリダイレクト。

予約一覧表示（管理画面）
1. Controller が Service に `status`, `date`, `query` を渡す。
2. Service が予約一覧、集計、時間帯サマリーを組み立てて返す。
3. View は受け取ったデータを描画する。
